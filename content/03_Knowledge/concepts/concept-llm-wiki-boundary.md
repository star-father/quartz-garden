# LLM Wiki 适用边界（个人 vs 企业）

> **类型**: concept
> **定义**: LLM Wiki 编译模式并非万能，其最优适用场景与受限场景的边界。

## 定义

LLM Wiki 编译模式 = 以 LLM 为编译引擎，把 `raw/` 原料自动抽离为结构化 wiki 页面（概念/方法/笔记），配本地文件存储 + 索引 + 检索的知识管理体系。

## 为什么重要

明确边界可避免两类错误：
- **过度承诺**：把个人知识库方案直接套企业，踩权限/协作坑
- **过早放弃**：因企业难点否定个人场景价值

## 适用：个人知识系统（强匹配）

| 优势 | 说明 |
|---|---|
| 自动结构化强 | LLM 编译自动抽离概念/方法，无需手动分类 |
| 本地文件易控 | 纯 `.md` + Git，数据主权在本地 |
| 成本可接受 | 个人量级（百~千页）摄入/检索成本可控 |
| 单人决策链短 | 无需权限审批，AI 编译 + 人归档即可 |

→ 本库 `D:\work_place\place` 即典型个人知识系统实例（见 [[method-ai-obsidian-kb-build]]）。

## 受限：企业知识库（需额外工程改造）

| 难点 | 说明 | 改造方向 |
|---|---|---|
| 维护成本高 | 页面量 × 协作频率放大 lint/ingest 成本 | 自动化巡检 + 专人治理 SOP |
| 多人协作弱 | 当前单工作区 + Git 分支模型不适合并发编辑 | 接权限系统 / 数据库后端 |
| 权限薄弱 | 本地 `.md` 无细粒度权限 | 接企业网盘 / 知识库平台 API |
| 需额外工程 | 检索/去重/版本需从脚本升级为服务 | 容器化 + API 网关 |

> ⚠️ 若未来涉及团队/企业场景，应先评估上述改造成本，不盲目套用个人模式。

## 边界与反例

- **反例**：把本库直接给 10 人团队当共享知识库 → 权限/并发冲突爆发
- **灰度**：1~3 人小团队 + 只读分发（如企微卡片推送）可接受，但编辑权仍集中单人
